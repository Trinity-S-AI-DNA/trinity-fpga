# tri fpga build — openXC7 bitstream pipeline

## Module

tri.fpga.build

## Description

The four-tool openXC7 flow — yosys, nextpnr-xilinx, fasm2frames, xc7frames2bit —
as `tri` subcommands, so the steps and their preconditions live in one place
instead of in a shell history.

The value is not the four invocations; those are short. It is the six traps
between them, each of which costs a failed run and none of which announces
itself. Every one below was hit for real, most of them on 2026-08-20:

1. `synth_xilinx` takes **`-family xc7`**, not `-arch xc7`. With `-arch` yosys
   exits non-zero with a usage error that reads like a bad script.
2. `--db-root` is the **family** directory (`.../prjxray-db/artix7`), never the
   part directory. Pointing at the part yields *"Mapping file
   .../mapping/devices.yaml does not exist"*, which sounds like a corrupt
   database.
3. The chipdb must be generated from the **same tree** as the `nextpnr-xilinx`
   binary. A chipdb from another revision aborts on an internal-ID assertion
   that names neither the file nor the revision.
4. `bbaexport.py` needs **two** submodules: `prjxray-db` for `--xray` and
   `nextpnr-xilinx-meta` for `--metadata`. With only the first it dies on a
   missing `wire_intents.json` — again reading as database corruption.
5. On macOS the nextpnr build needs `-DUSE_OPENMP=OFF` (Apple clang has no
   `-fopenmp`) and `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` (cmake 4.x drops
   compatibility with the older minimum this project declares).
6. `regymm/openxc7` lags the tree by months. On 2026-08-20 its bundled binary
   (`45a986b`) failed to place a BUFR that current `main` places fine — a bug
   that had already been fixed. **A stale image reproduces bugs that no longer
   exist**, and the resource table it prints (`BUFR: 0/20`) corroborates the
   wrong conclusion, because that table counts bels by site type and reports
   them available whether or not anything can bind to them.

## Commands (as tri subcommands)

- `build`   — `.v` + `.xdc` → `.bit`. Flags: `--top`, `--part`, `--seed`,
              `--chipdb`, `--out`, `--keep-intermediates`.
- `chipdb`  — generate and cache `<part>.bin` from a nextpnr tree.
              Flags: `--part`, `--nextpnr-root`, `--out`.
- `doctor`  — check the preconditions and report which of the six traps the
              current environment is standing in, without building anything.
- `flash`   — `openFPGALoader` with a rescanned busdev. Flags: `--bit`,
              `--cable`.

`doctor` exists because five of the six traps are detectable before the first
tool runs, and each otherwise surfaces as a failure attributed to the wrong
stage.

## Types

```zig
pub const Part = struct {
    name: []const u8,          // "xc7a200tfbg484-2"
    family: []const u8,        // "artix7" -- derived, never passed as a part dir
};

pub const BuildSpec = struct {
    sources: []const []const u8,
    constraints: []const u8,
    top: []const u8,
    part: Part,
    seed: u32 = 1,
    chipdb: ?[]const u8 = null,   // cached; generated on demand when null
    out: []const u8,
};

pub const StageResult = struct {
    stage: enum { synth, pnr, frames, bitstream },
    exit_code: u8,
    duration_ms: u64,
    artifact: ?[]const u8,
    /// Set when a known trap is recognised in the stage's output, so the
    /// report names the cause rather than the symptom.
    diagnosis: ?[]const u8 = null,
};
```

## Behaviors

### build produces a bitstream from sources and constraints

- **given** a `.v` set, an `.xdc`, a part, and a chipdb for that part
- **when** `tri fpga build --top top --part xc7a200tfbg484-2` runs
- **then** four stages run in order and a `.bit` is written, and each stage's
  exit code, duration, and artifact are reported

### build refuses a chipdb from a different revision

- **given** a chipdb generated by a different `nextpnr-xilinx` than the one on PATH
- **when** the pnr stage aborts on the internal-ID assertion
- **then** the failure is reported as *"chipdb revision mismatch — regenerate
  with `tri fpga chipdb`"*, naming both revisions, rather than passing the raw
  assertion through

### doctor reports the traps without building

- **given** any environment
- **when** `tri fpga doctor` runs
- **then** it reports, for each of the six preconditions, whether it holds —
  and exits non-zero if any that would break a build does not

### doctor catches the stale-image trap

- **given** a `nextpnr-xilinx` whose version predates the tree it is being used against
- **when** `doctor` runs
- **then** it reports the version and warns that a lagging binary reproduces
  fixed bugs, because that failure is indistinguishable from a real one at the
  point where it appears

### chipdb caches across builds

- **given** a previously generated `<part>.bin` and an unchanged nextpnr revision
- **when** `build` runs
- **then** the cached chipdb is reused and the export is skipped

## Implementation

Subcommands of `tri`, in `src/tri/fpga_build.zig`. No separate binary — the
convention `specs/storm_main.md` states.

## Notes on scope

This spec covers the **build** flow. `tri fpga build-uart`, `flash-uart`,
`uart-test` and `status` are named in CLAUDE.md against `src/tri/tri_fpga.zig`
and are not re-specified here.

The pipeline is deliberately **not** expressed in TRI-27. The `.t27` instruction
set across all 69 specs in this repo is `MOV RET CMP ADD SHR JZ LDI HALT SHL MUL
AND JEQ JGE OR JMP JUMP LD JNE SUB ST JLT JGT` — arithmetic, branches, and
register/memory moves, with no instruction that reaches the host. `LD`/`ST`
address the machine's own memory, not the filesystem. A build orchestrator needs
to spawn processes and read files, so it belongs in the Zig layer; `.t27` is the
ISA that numeric kernels compile down to, underneath this.
